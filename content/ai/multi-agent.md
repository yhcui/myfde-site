## 先泼冷水

「多智能体」是这个领域被过度消费的概念。**一个 Agent 加几个好用的工具，能覆盖大多数业务场景**；拆成多个 Agent 的系统，调试难度和 token 成本都按乘法涨。

所以这一篇先给结论：**默认用单 Agent，除非出现下面三个信号之一。**

## 三个拆分信号

1. **上下文互相污染**：一个任务里「发散找资料」和「严格按格式输出」放进同一个窗口，前者总是干扰后者——拆开各自维护干净上下文；
2. **流程天然多角色**：写方案的和审方案的不能是同一个「脑子」——审查 Agent 用另一套标准挑刺，才能发现执行 Agent 的盲区；
3. **需要真并行**：多路调研可同时进行（各自调 API、各自读文档），串行太慢。

三个都没有？回到单 Agent。

## 三种拓扑

| 拓扑 | 结构 | 适用 | 成本 |
|------|------|------|------|
| 规划-执行 | 一个 planner 拆解任务，worker 执行，planner 汇总 | 任务步骤不确定，需动态拆解 | 中 |
| 流水线 | A→B→C 依次加工（如：检索→写作→审校） | 步骤固定、各步技能不同 | 低-中 |
| 辩论/评审 | 多个 Agent 互评或对抗后裁决 | 判断类任务、需要减少单一偏见 | 高 |

## 成本账

拆分前算三笔：**token 数** ≈ 单 Agent 的 N 倍（每个都有完整系统提示）；**延迟** ≈ 轮次数 × 单轮时间；**调试**——出了错你要在 N 份对话记录里定位是哪个环节把指令传歪了。

经验值：把 Multi-Agent 系统的评估集建好（见《[Evals](/ai/evals-intro/)》）再谈优化，否则连「拆了有没有变好」都答不上来。

## 起步建议

- 第一版永远单 Agent；
- 拆分一次只拆一个维度（先拆「执行与审查」，跑稳了再拆别的）；
- 每个新增 Agent 都要有存在的明确定义：它管什么上下文、它为什么不能是工具。
