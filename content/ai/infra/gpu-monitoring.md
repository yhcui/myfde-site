## 三个最常被误读的指标

**SM 利用率（GPU Util）**
显示 90% 不等于「满载」——它度量的是「有 kernel 在跑的时间占比」，**不看计算是否喂饱**：显存带宽瓶颈、串行等待都能让它虚高。判断真实瓶颈要结合吞吐数据：「利用率 90% 但 tokens/秒上不去」= 瓶颈在别处（见《[吞吐与延迟](/ai/infra/throughput-latency/)》）。

**显存占用**
危险的不是「用了多少」而是**余量还能容纳几路新请求的 KV Cache**——显存打满的前兆是新请求排队或直接失败（见《[显存账本](/ai/infra/vram-ledger/)》《[KV Cache](/ai/infra/kv-cache/)》）。告警阈值应该设在「余量 < 预计峰值并发所需」时，而不是「用了 95%」时。

**功耗与温度**
GPU 有功耗墙与温度墙——撞墙自动降频，表现为「下午吞吐莫名下降」：机房温度、散热积尘、相邻卡互烤都是现场常见原因。**降频是慢性事故**，不告警就一直在线没人发现。

## 四条告警阈值建议

| 告警 | 阈值方向 | 说明 |
|------|----------|------|
| KV 余量 | 余量 < 峰值并发预估 | 显存事故的前置指标 |
| 请求排队 | 队列深度持续 > 0 超过 N 秒 | 容量不足的早期信号（见《[弹性伸缩](/ai/infra/autoscaling/)） |
| 温度/功耗 | 持续贴近温度墙 | 降频风险，查散热 |
| TTFT 劣化 | P95 超过 SLO 的 80% | 体验告警打在崩溃之前 |

## 工具与频率

`nvidia-smi` / DCGM 类 exporter 拉指标进现有监控栈即可——**推理服务的 GPU 监控不需要新工具，需要的是新阈值**：把上面四条配起来，比装十套面板有用。看板每天扫一眼趋势（下午降频型事故靠趋势发现），告警交给阈值。

## 小结

GPU 监控的三个坑：把利用率当满载、把显存占用当余量、把降频当玄学。**推理服务的监控要打在「下一路请求还能不能进来」上**——这就是 KPI 与 SLA 的区别。
