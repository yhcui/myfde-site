## 机制：为什么需要它

模型逐 token 生成，每生成一个新 token，都要「重读」前文所有 token 的注意力中间结果。如果每步都重算全部历史，复杂度是平方级的——生成到第 1000 个 token 时，要把前 999 个全部重算一遍。

**KV Cache 把每层的 Key/Value 中间结果存下来，后续步骤直接复用**——用显存换计算，把每步成本从「重读全部历史」降到「只算新来的一个」。

代价是显存：**缓存大小随上下文长度线性增长**，且按并发人数各自独立——这是推理服务显存账本的第二大项（第一项是模型权重，见《[显存账本](/ai/infra/vram-ledger/)》）。

## 两个直接推论

1. **上下文长度是显存奢侈品**：支持 128K 长文本的并发能力和 8K 的完全不是一个量级——评估服务容量时，看的是「多少并发 × 多长上下文」的乘积，不是并发数本身；
2. **缓存命中 = 便宜**：固定长前缀的 KV 结果可以跨请求复用——这就是各家「提示词缓存」折扣的物理基础（见《[上下文工程](/ai/context-engineering/)》的排序原则）。

## PagedAttention：把虚拟内存的思想搬进显存

传统实现里每个请求的缓存是一整块连续显存，按「最大可能长度」预留——就像没有分页的内存管理，浪费严重，长请求直接吃满。

vLLM 的 PagedAttention 把缓存切成小块（页），按需分配、请求间共享物理页——**操作系统 101 的思想**：碎片少了、并发上去了。这就是 vLLM 吞吐显著领先的第一性原因，不需要记住实现细节，记住这个类比就够用了。

## 对 FDE 的意义

客户问「为什么这么吃显存」「为什么长文档贵」，答案都指向 KV Cache。**能把这个机制讲给客户听的人，才谈得上在现场调优它**——显存不够时砍上下文、砍并发还是换量化，是这一组后面几篇的主题：《[连续批处理](/ai/infra/continuous-batching/)》《[量化](/ai/infra/quantization/)》。
