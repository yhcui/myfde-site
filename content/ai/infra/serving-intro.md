## 先回答：为什么要自建

绝大多数项目**该从调 API 开始**——按量付费、零运维、模型随时代升级。自建推理服务的理由只有三条，每条都要过硬：

1. **合规红线**：客户数据出不了内网/机房（金融、政务、医疗的常见硬约束）——这是 FDE 场景里最常见的真实理由，见《[私有化决策树](/ai/infra/private-deploy-tree/)》；
2. **成本拐点**：调用量大到 API 账单超过自持成本拐点——通常发生在高并发、固定负载的业务上，**先算清账再迁移**（算账方法见《[Token 经济学](/ai/token-economics/)》）；
3. **深度定制**：需要控制采样策略、注入自研缓存、做延迟极限优化——应用层做不到的那些。

三条都不占，别自建；占一条，往下读。

## 一个推理栈的四个组成部分

| 部分 | 职责 | 常见选择 |
|------|------|----------|
| **模型资产** | 权重与配置 | 开源模型 + 量化版本（见《[量化入门](/ai/infra/quantization/)》） |
| **推理引擎** | 真正跑模型、管理显存与批处理 | vLLM 等专用引擎（见《[框架横评](/ai/infra/serving-frameworks/)》） |
| **服务层** | API 协议、鉴权、路由 | 网关 + OpenAI 兼容接口 |
| **运维层** | 监控、扩缩容、升级回退 | 指标 + 编排（见《[可观测](/ai/infra/observability/)》） |

认知排序：**引擎决定成本与性能的上限，运维决定事故的下限**——新手把 90% 时间花在引擎选型，老兵把一半时间花在运维设计。

## 自建的第一天该做什么

1. 用最省事的方式跑通（一行命令级别的本地推理工具），确认硬件与模型匹配；
2. 用**客户真实问题**建一个 20 条的冒烟评估集——这是后面所有选型决策的裁判；
3. 压测拿到自己的基线数字：吞吐、首 token 延迟、并发上限。

有了这三样，你才有资格谈选型——推理服务的所有话题，本质上都是在这三样数字之间做交易。
