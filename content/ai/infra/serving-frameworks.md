## 先分清两类工具

- **推理引擎**：vLLM、TGI、SGLang、LMDeploy——生产服务的核心，追求吞吐与延迟；
- **本地运行器**：Ollama、LM Studio 一类——开发与个人使用的「一行命令」方案。

错配的典型事故：拿 Ollama 顶生产高并发（它是为易用性而非吞吐设计）；或在笔记本上折腾 vLLM 集群（开发体验为负）。

## 横评表

| | 定位 | 强项 | 边界 |
|---|------|------|------|
| **vLLM** | 生产推理的默认答案 | PagedAttention + 连续批处理，生态最广，OpenAI 兼容接口 | 显存管理激进，混布其他 GPU 任务要小心 |
| **TGI**（Hugging Face） | HF 生态的原生服务 | 稳健、企业集成好 | 社区声量与迭代速度逊于 vLLM |
| **SGLang** | 高性能新锐 | 结构化输出与复杂调度场景强势 | 更年轻，生产案例积累少一档 |
| **LMDeploy** | 国产出品，全栈工具链 | 量化部署一体，对国产硬件生态友好 | 国际社区小 |
| **Ollama** | 本地开发运行器 | 一行命令跑模型，跨平台 | 面向个人，非并发服务设计 |

## 场景决策表

- 客户私有化部署的生产服务 → **vLLM**（保守稳妥）
- 已经全栈 Hugging Face → **TGI**（一致性优先）
- 结构化输出/复杂工作流高性能要求 → 评估 **SGLang**
- 国产化环境 → 评估 **LMDeploy**
- 开发本机/演示环境 → **Ollama**

## 两条选型原则

1. **选无聊的**：推理引擎是地基，激进尝鲜的成本是全站事故——默认项（vLLM）没有明显不满足需求时就不换；
2. **留退路**：业务代码只依赖 OpenAI 兼容接口，不锁死任何引擎——换引擎那天你的业务代码零改动，评估集（见《[Evals](/ai/evals-intro/)》）就是迁移验收的裁判。

## 小结

框架会继续换代（这个表半年后就该复查），但**评估集 + 接口解耦**这两样让你永远换得起。相关：《[KV Cache](/ai/infra/kv-cache/)》《[连续批处理](/ai/infra/continuous-batching/)》——看懂这两个机制，就看懂了横评表的评分标准。
