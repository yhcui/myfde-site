## 四段解剖

一次「提问→答完」的时间，拆开是四段：

```
[排队] → [预填充 prefill] → [解码 decode] → [网络/客户端]
 等批里的空位   吃进你的提示词      一个个吐 token    传输与渲染
```

**TTFT ≈ 排队 + 预填充**；**TPOT ≈ 解码的单步时间**——两个用户感知指标分别由不同段落决定，优化必须先定位段落再动手（见《[吞吐与延迟](/ai/infra/throughput-latency/)》）。

## 各段落由什么决定

- **排队**：负载 vs 容量。批饱和、副本不足都会拉长它（见《[弹性伸缩](/ai/infra/autoscaling/)》）；
- **预填充**：与**提示词长度成正比**——这是「上下文工程=成本工程=延迟工程」三位一体的地方（见《[上下文工程](/ai/context-engineering/)）：塞 2 万 token 的材料，TTFT 先吃一大截；
- **解码**：由模型大小、量化档位、批内分时决定——单步下不去就是模型档位问题（见《[量化](/ai/infra/quantization/)》）；
- **网络**：客户端流式渲染、网关转发——占比通常小，但 SaaS 跨境调用例外。

## 症状-段落-处方对照表

| 症状 | 段落 | 处方 |
|------|------|------|
| 首 token 慢，答起来流畅 | 排队/预填充 | 扩容量；砍提示词长度；高频前缀进缓存 |
| 首 token 快，整体慢 | 解码 | 换小一档模型/量化；检查降频（见《[GPU 监控](/ai/infra/gpu-monitoring/)》） |
| 间歇性尖刺 | 排队 | 批饱和或长请求独占——限长度上限、调批策略 |
| 夜里快白天慢 | 全局 | 散热降频或业务峰谷——先看监控曲线再猜 |

## 压测才可信

拆解不能靠推断：压测时把四段时间分别打点（引擎普遍暴露这些指标），**让数据指出哪段超预算**——「感觉是模型慢」在现场十次有八次是排队。

## 小结

延迟治理的纪律：**先拆段、再处方**。四段各有各的药，混着吃只会互相抵消。这一页加上《[可观测](/ai/infra/observability/)》，就是推理服务性能事故的完整急救包。
