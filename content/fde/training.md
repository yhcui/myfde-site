怎么训练成一个 FDE？我按这个站的主题把路线拆成五个公里桩——K0 到 K4。它不是课程大纲，是我自己正在走的路线，每个 K 附自检清单：**过不了清单，就不要进入下一桩**。

如果你还不确定 FDE 是什么，先读《[FDE 是什么——中文完全指南](../what-is-fde/)》。

## K0 通行能力（公里桩 0）

FDE 的入场券是工程能力，不是论文。K0 要凑齐三样东西：

- **一门能交付的工程语言**：Python（Agent 生态第一语言）或 Java。能写服务、调 API、处理数据、看懂报错；
- **LLM API 的肌肉记忆**：调用主流大模型 API、控制成本、处理长上下文、知道 prompt 的基本套路；
- **把技术讲给人听的能力**：给非技术的人讲清楚一个 AI 系统能做什么、不能做什么。FDE 日常一半的失败在这里。

**K0 自检清单：**

- [ ] 能不查文档写出一个调用 LLM API 的小脚本
- [ ] 给家人讲清楚「大模型为什么会一本正经地胡说八道」，并让对方听懂
- [ ] 用 Python 写过一个带输入输出的完整小工具（不是 notebook 玩具）

## K1 第一个完整部署（公里桩 1）

FDE 的身份证明不是「会用什么框架」，而是**独立完成过一次从需求到上线的完整部署**。走一遍六步闭环：

1. **需求勘察**：找一个真实的人（同事、朋友的公司都行），问出他最烦的一个重复性工作；
2. **方案设计**：确定哪些环节交给模型、哪些写死规则、哪些留给人；
3. **开发**：最小可用版本，别追求漂亮；
4. **部署**：放到真实环境运行——一台云服务器或公司内网都行，不能只躺在本地；
5. **反馈**：让真实用户用一周，收集抱怨；
6. **迭代**：根据抱怨改一版，再跑一周。

**K1 自检清单：**

- [ ] 有一个不是我一个人在用的 AI 应用，真实用户用了两周以上
- [ ] 经历过至少一次「用户真正想要的和说的完全不一样」
- [ ] 处理过至少一次线上翻车（报错、超限、数据异常）

## K2 工具箱（公里桩 2）

有了完整闭环，再把工具箱补齐。FDE 驻场时没时间从头造轮子：

- **Agent 框架**：LangChain（生态最全）、AutoGen（多 Agent 协作）、CrewAI（角色分工）、Dify（低代码快速搭建）——入门对比见《[AI Agent 入门指南](/ai/agent-intro/)》；
- **RAG 与向量数据库**：知识库问答是企业需求里出现频率最高的一类，检索增强生成的完整链路要亲手搭过；
- **评估**：会写简单的测试集，能量化「改了 prompt 之后到底变好还是变坏」；
- **部署运维基本功**：Docker、反向代理、日志、监控告警。

**K2 自检清单：**

- [ ] 至少两个框架各搭过一个非 Demo 的东西
- [ ] 搭过完整 RAG：文档解析 → 切分 → 向量化 → 检索 → 生成
- [ ] 有一次「用数据说服自己别乱改」的经历

## K3 行业纵深（公里桩 3）

K2 之后你和多数人差不多，K3 才是护城河：**选一个行业，钻进去**。金融、医疗、制造、政务——选你能拿到真实场景的那个。行业知识无法速成，只能浸泡：读行业报告、混行业社群、找行业内的人聊业务流程。

FDE 的定价能力来自「懂这个行业的技术人」这个交集，而不是技术单点。

**K3 自检清单：**

- [ ] 能说清所选行业的 3 个真实业务痛点与 AI 的对应解法
- [ ] 认识至少 5 个该行业的从业者并保持联系
- [ ] 用行业语言（不是技术语言）写过一篇分析

## K4 现场方法论（公里桩 4）

最后一块是 FDE 真正的手艺——到了客户现场怎么干活。四步法：

1. **勘察**：先听、先看、先记，头几天别急着给方案；
2. **对齐**：把「客户说的」翻译成「客户要的」，白纸黑字确认范围；
3. **小步交付**：每周交付一个可用的增量，让信任随进度累积；
4. **撤离**：系统独立运行、文档齐备、可复用部分沉淀，然后干净地撤出。

现场生存守则：会议室里达成的共识 ≠ 真实业务流程；Demo 效果 ≠ 生产效果；永远给自己留一个「本周可交付」的最小版本。

**K4 自检清单：**

- [ ] 在真实客户/合作方面前做需求确认并白纸黑字对齐过
- [ ] 有一次「砍掉范围保交付」的实战经历
- [ ] 写过一份别人只看文档就能接手的交接材料
