工程师转 AI，别从模型开始，从 Agent 开始

给要转 AI 的工程师：为什么「先去学模型」是低效路线，而 Agent 工程是复用率最高的切入点——三个论据、一条五步路线和常见误区。

被广泛流传的转型建议，恰恰是低效的那条

你要转 AI，搜到的攻略大概率长这样：先补线性代数，再看吴恩达课程，然后学 PyTorch，复现两个经典模型，投算法岗。

这条路线对博士生成立，对有几年经验的工程师基本不成立。原因不是你学不动，而是它押错了价值层。

三个论据

论据一：模型已经是 API，不是技能。

模型层在急速商品化——能力每半年换代，今天深学的训练细节，下个版本就被新范式作废。而「调用模型做业务」的知识半衰期长得多：上下文管理、工具调用、评估方法、系统集成，这些三年后依然成立。

押注哪一层，看稀缺性在哪：会训模型的人，市场上按千计；能把模型稳定塞进生产系统的人，按万计缺口。

论据二：企业的钱花在应用层。

绝大多数公司不训练模型——他们买 API，然后卡在「怎么接进业务」：数据在哪、权限怎么过、出错谁兜底、效果怎么验证。这正是 FDE（前沿部署工程师）这类角色在 Anthropic、Palantir 的招聘里批量出现的原因：模型越强，「最后一公里」的工程缺口越大。读一读这些公司的岗位描述你会发现，要求清单里是系统集成、客户现场、交付能力——不是论文。

论据三：你的资产复用率。

工程师转方向，本质是计算资产复用率。列一下你手上的东西：系统设计、API 对接、数据建模、调试排障、部署运维、权限与安全——

  • 转模型研究：复用率不到两成，数学和实验范式要从头练；
  • 转Agent 工程：复用率六成以上——Agent 的日常就是「模型 + API + 数据 + 部署」，你只是把其中一个组件从「内部服务」换成了「LLM API」。

复用率高的方向，转型速度快、转型后议价也高。

从 Agent 开始，具体走五步

每步都有明确的「完成标志」，做完再走下一步：

  1. 调通 API：用任何语言写脚本调用大模型 API，处理流式输出与超时重试。完成标志：一个能稳定跑的命令行问答工具。
  2. 单 Agent + 工具：给模型挂 2-3 个工具（查询、写文件、调内部接口），跑通「模型决策→执行→回传→再决策」循环。这是 Agent 的最小骨架。
  3. 接上知识：RAG：给 Agent 加检索——文档切分、向量化、召回、注入上下文。完成标志：一个能答对内部文档问题的问答服务。
  4. 组合：工作流与多 Agent：把任务拆成规划/执行/审查多个环节，用框架（LangChain、AutoGen 等）编排。完成标志：一个三步以上的自动工作流，能处理一次失败并重试。
  5. 质量与护栏：Evals：给上面所有东西加评估集和边界控制。这一步决定你是「会做 Demo」还是「能交付」——也是面试里区分度最大的一步。

配套细节在 FDE 训练路径，每阶段有自检清单。

常见误区

「要不要补数学？」 理解 transformer 注意力机制的直觉够用，系统补数学的性价比不如把第 5 步做扎实。真要走研究路线是另一码事，但那不是「转 AI」，是「转学术」。

「模型越来越聪明，Agent 工程会不会被淘汰？」 恰恰相反。模型越强，被淘汰的是「套壳 Demo」，涨身价的是「整合工程」——因为客户敢把更关键的业务交给你自动化，集成、评估、兜底的要求只会更高。这和云计算的历史一致：云越强，运维没有消失，升级成了 SRE。

「没有 AI 项目经验，简历怎么写？」 用这五步路线自己造经验——第 3 步做出来的内部文档问答、第 5 步搭起来的评估流水线，本身就是项目经历。开源出来，比任何培训证书都硬。

结论

转型不是清零重来，是把「模型」这个新组件装进你现有的工程体系里。从 Agent 开始，你过去十年的积累全程在场——这就是最短路径。
