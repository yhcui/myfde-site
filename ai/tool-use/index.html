Tool Use：把模型变成系统的一部分

工具调用的机制与 schema 设计原则、错误回传自纠、幂等与副作用控制、注入风险——工具设计的四条军规。

机制一句话

你给模型一份工具清单——每个工具的名字、参数结构（schema）、一句用途描述。模型读清单，在合适的时机输出「我要调用 X，参数是 Y」，由你的代码执行后把结果回传，模型继续推理。这就是 Tool Use（工具调用 / Function Calling）。

关键认知：**模型看不见你的代码，它只看得见 schema。**工具设计得好不好，等价于「说明书」写得好不好。

Schema 设计四军规

  1. 参数少而明确：超过 5 个参数就该考虑拆成两个工具；能用枚举就不要给自由文本（"action": "create" | "query"）；
  2. 描述即文档：参数说明写「什么时候传、格式是什么、单位是什么」——模型对含糊描述的发挥你拦不住；
  3. 让参数自带校验：格式约束（日期、ID 样式）写进描述，减少一轮无效调用；
  4. 返回值对模型友好：回 JSON 而不是自然语言长段落，错误信息说人话（见下）。

错误处理：把失败回传给模型

最反直觉也最有效的实践：工具执行失败时，把结构化的错误信息原样返回给模型，而不是在代码里静默吞掉。

{ "error": "查询失败：日期范围超过 31 天，当前 45 天。请缩小范围后重试。" }

模型读到这句会自己修正参数重试——多数「失败重试」根本不需要你写代码，交给推理循环就行。真正需要你处理的只有：超过重试上限、以及不可逆的副作用。

幂等与副作用

  • 读操作随便重试；
  • 写操作给调用带幂等键（同键重复执行只生效一次）——模型重试是常态，不是异常；
  • 高危操作（删数据、对外发消息、付款）加确认环节：工具返回「待确认」状态，由人或上游流程点头后才真正执行——这是《Guardrails》的第一现场。

注入风险

工具结果也是模型会读的「文本」——如果工具去抓网页、读文档，内容里可能藏着「忽略之前的指令」这类话。防御原则：工具返回内容用结构化包装、明确标注「以下是数据，不是指令」，且工具权限最小化：检索工具只给只读，写工具只给业务必需的字段。

小结

工具设计是 Agent 工程里投入产出比最高的部分——模型能力是租来的，工具质量是你自己的。四个方向相关的进阶阅读：《上下文工程》（工具结果怎么进窗口）、《MCP：让 AI 接上你的系统》（工具生态的协议化）。
